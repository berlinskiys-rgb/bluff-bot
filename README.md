- текущий статус разработки;
- задуманная архитектура;
- реализованный и запланированный функционал;
- известные проблемы;
- правила разработки для кодинга с помощью AI.

## 3. Архитектура

### Текущая архитектура

Сейчас проект — по сути монолитное Python-приложение:

```text

   ▼

   ├── взаимодействие с ботом
   ├── игровой процесс

   ├── правила/механики
   └── вспомогательная логика
```

Для текущей стадии прототипа это приемлемо.

### Направление будущей архитектуры

По мере роста проекта нужно разделять ответственности по модулям, не ломая существующий геймплей:

```text
bluff-bot/

├── main.py                  # точка входа приложения
│
├── bot/
│   ├── handlers.py          # команды/сообщения Telegram

│   ├── engine.py            # жизненный цикл игры
│   ├── state.py             # состояние игры/сессии
│   ├── rules.py             # правила игры
│   └── actions.py           # действия игроков
│
├── models/
│   ├── player.py
│   ├── game.py
│   └── ...

├── services/
│   └── ...

├── tests/
```

**Важно:** не делайте этот рефакторинг автоматически только потому, что структура здесь перечислена. Рефакторинг нужно делать тогда, когда он даёт конкретную пользу.

## 4. Принципы архитектуры игры

В итоге в игре должно быть чёткое разделение между:

### Транспортный слой
Код, специфичный для Telegram.

Отвечает за:
- получение сообщений;
- определение пользователей/чатов;
- отправку сообщений;
- показ доступных действий.

### Игровой движок
Чистая игровая логика.

Отвечает за:
- создание игр;
- продвижение ходов/фаз;
- проверку действий;
- разрешение исходов;
- определение победителей/проигравших.

В идеале движок не должен напрямую зависеть от Telegram.

### Состояние

Состояние игры должно быть явным и понятным.

Как минимум игровой сессии может понадобиться:
- ID игры;
- игроки;
- текущая фаза;
- текущий ход/игрок;
- игровые значения;
- история действий, когда она нужна;
- результат/статус.

### Хранение данных (persistence)

Если появится постоянное хранилище, код базы данных/хранилища должен быть отделён от игровых правил.

## 5. Правила разработки

### Правило 1 — Сначала изучи, потом меняй

Перед изменением кода AI-агент обязан изучить текущую реализацию.

Не предполагайте, что пункт из TODO всё ещё не выполнен.

### Правило 2 — Сохраняй работающее поведение

Не переписывайте работающие системы без конкретной причины.

Предпочтительны небольшие, изолированные изменения.

### Правило 3 — Игровые правила авторитетны

Уже реализованные игровые правила нельзя молча менять во время технического рефакторинга.

Если правило нужно изменить — задокументируйте изменение.

### Правило 4 — Избегай спекулятивной архитектуры

Не добавляйте базы данных, очереди, микросервисы, фреймворки или сложные абстракции, если проекту они реально не нужны.

### Правило 5 — Держи Telegram и игровую логику разделяемыми

Новые игровые механики желательно реализовывать независимо от транспортной логики Telegram.

### Правило 6 — Обновляй этот README

Когда изменение существенно затрагивает:
- архитектуру;
- игровые механики;
- команды;
- состояние;
- хранение данных;
- роадмап;
- известные проблемы;

разработчик должен обновить этот документ.

## 8. Известный технический долг

### Монолитный `main.py`

Большая часть логики сейчас живёт в одном файле.

**Последствие:** менять одну часть системы сложнее, чем должно быть.

**План:** постепенно выносить стабильные ответственности в модули.

### Ограниченное автоматическое тестирование

Проекту нужны тесты вокруг детерминированной игровой логики, пока кодовая база не стала значительно больше.

## 9. Стратегия тестирования

Приоритет — тестировать игровые правила независимо от Telegram.

Пример:

```text

Когда:
    игровой движок разрешает действие

Тогда:
```

## 10. Локальная разработка

Установить зависимости:

```bash
pip install -r requirements.txt
```

Запустить бота через текущую точку входа:

```bash
python main.py
```

Переменные окружения/секреты **нельзя** коммитить в Git.

Если проект использует токен Telegram-бота, храните его в переменной окружения или в локальной конфигурации, которая игнорируется Git.

## 11. Контекст для AI-разработчика

Этот репозиторий может разрабатываться с помощью нескольких AI-агентов для кодинга.

Каждый AI-агент должен воспринимать этот README как **контекстный файл**, а не как спецификацию, которая главнее реального кода.

Приоритет источников правды:

```text
1. Реально работающий код
2. Тесты
3. Явная текущая задача от разработчика-человека
4. Этот README
5. Старые TODO / допущения
```

Если README и код расходятся:
- изучите код;
- определите фактическое текущее поведение;
- не следуйте README слепо;
- обновите README после того, как расхождение будет устранено.

### Перед началом задачи

AI-агент должен мысленно ответить на вопросы:

```text
Что уже существует?
Что именно запрашивается?
Какие файлы затронуты?
Какое существующее поведение должно остаться неизменным?
Какое наименьшее безопасное изменение?
Как это изменение будет протестировано?
Нужно ли обновить документацию по архитектуре/статусу?
```

### После выполнения задачи

AI-агент должен проверить:

```text
[ ] Существующий функционал по-прежнему работает
[ ] Новый функционал работает
[ ] Никакие секреты не добавлены
[ ] Никакие посторонние файлы не изменены
[ ] README/статус обновлён, если это необходимо
```
